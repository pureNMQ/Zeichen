# Zeichen Memory

在每个相关工作开始时按需检索项目共享记忆；只记录可复用、可核对且对未来协作有价值的内容。记忆是上下文层，不替代需求、任务、Wiki、评论或活动记录。

## 基本边界

- 仅使用当前项目的 `memory.*` 工具。项目与会话范围由 Zeichen 管理。
- `memory.remember` 写入当前 Agent 的会话缓存，不等于写入长期记忆；`memory.improve` 才会异步蒸馏该会话。仅 `memory.improve_status` 返回 `completed` 才代表蒸馏成功。
- 记忆检索结果是待核对的历史上下文。作为事实或决策依据前，必须用相关 Requirement、Task、Wiki、评论或可验证证据核对；不确定、过时或相互矛盾时，明确其不确定性。
- 不记录密钥、令牌、密码、个人敏感信息、未获授权的第三方数据，或大段对话、代码和文档。
- 需求、任务、状态、验收、实施证据和正式结论仍应写入相应协作实体；不要以“已写入记忆”代替协作记录。

## 检索与使用

1. 在任务依赖既往项目结论、用户偏好、历史调查、已知风险或相似处理经验时，先用 `memory.recall` 提出具体问题。一般无需向用户逐次确认检索。
2. 仅在需要当前会话的连续上下文时传入稳定的 `session_id`；需要项目级历史时省略它。不要把不同工作流、用户请求或项目复用为同一会话。
3. 将召回结果与当前协作记录核对，再说明哪些内容已证实、哪些只是历史线索，以及它如何影响当前操作。
4. 没有召回结果或工具不可用时，继续使用可获得的项目记录；不得虚构记忆内容或暗示已检索成功。

## 记录会话记忆

仅在内容满足以下任一条件时使用 `memory.remember`：可复用的事实、已核对的决策及其理由、稳定偏好、已验证的排查结论、风险边界，或后续工作必需的交接信息。

1. 先确认内容已核对、足够简短且脱离当前对话仍可理解；标明事实、决定、证据来源或尚未确认的部分。
2. 使用本次业务工作的稳定 `session_id`。不要用临时随机值，也不要与无关工作共享。
3. 有明确关联实体时传入 `anchor`：`{ "entity_type": "requirement|task|document", "entity_id": "<实体 ID>" }`。锚点必须同时包含类型和 ID，且不得伪造关联。
4. 记录成功后，只报告“已写入会话缓存”并附带记录内容摘要，不要称为已形成长期记忆或已沉淀官方结论。

示例：

```text
memory.remember(
  project_id: 当前项目,
  session_id: "requirement-reference-navigation",
  content: "已核对：需求和文档详情页的引用目前只显示实体 ID，且不可点击；修复需求已创建并关联相关证据。",
  anchor: { entity_type: "requirement", entity_id: "..." }
)
```

## 蒸馏为长期记忆

仅在一个会话已形成可复用的、经过核对的工作成果时，建议或按用户明确要求调用 `memory.improve`。对于成本、影响或范围明显的蒸馏，先说明要蒸馏的会话、预期价值和它不会替代的正式记录。

1. 调用 `memory.improve` 时使用当前 Agent 与该会话的 `session_id`；不得替其他 Agent、其他项目或不明来源的会话发起蒸馏。
2. 记录返回的 `job_id`，说明任务是异步的，不能把“已提交”称为“已完成”。
3. 使用 `memory.improve_status` 查询结果。只有 `completed` 时报告已形成长期记忆；`queued`、`running`、`upstream_busy`、`timed_out`、`failed` 或其他结果均应如实说明并保留下一步。
4. 不反复提交同一会话来规避进行中的冲突或超时；先检查已有任务状态，再由用户决定是否重试。

## 修正与删除

- 发现记忆错误、敏感或不应保留时，先定位具体条目，并说明删除影响；删除是不可恢复操作，必须取得用户针对该条目的明确确认后调用 `memory.forget`。
- 不得批量清空、猜测 `data_id`、或用删除来改写协作历史。更正后的正式事实应同步写入相应 Wiki、评论或业务实体。

## 失败处理

权限不足、服务不可用、检索为空、蒸馏失败或超时时，保留已核对的草稿和工作证据，报告实际状态及可执行的下一步。不得将本地笔记、聊天摘要或未完成的蒸馏冒充为项目共享长期记忆。
